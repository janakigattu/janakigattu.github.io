The wrong answer is already out. The question now is why it happened, what fixes it, and how you prove the fix before the assistant goes back live. Answer six questions and this review names the severity, the most likely root cause, and the five checks that must pass first.

How to run a failure review in your team

  1. Review the incident, not the person. The question is what the harness allowed, not who asked the question. A review that blames the user will miss the next failure.
  2. Reproduce it before you fix it. If you cannot make the failure happen again on demand, you cannot prove the fix worked. The retest set below is the proof.
  3. Fix the gate, not the answer. Correcting one wrong answer leaves the next one waiting. The fix names the harness gate that failed, so the same shape of failure cannot come back.
  4. Keep the assistant down until the retest passes. A Stop it now verdict means the assistant stays offline, or in a human reviewed queue, until all five retest checks pass.
  5. Write the incident down. The failure type, the root cause, and the fix go into the run log. The next review starts from that record instead of from memory.
